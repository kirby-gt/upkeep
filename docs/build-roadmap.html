Build plan · vertical slices

Upkeep Build Roadmap

From the working prototypes to a self-hosted production system on your VPS — thirteen slices, each one a complete cut from database to browser that you can actually use before the next slice starts.

Hono API PostgreSQL (dedicated container) Drizzle migrations Self-rolled session cookies MinIO / volume storage SSE + polling Caddy reverse proxy pg_dump backups

A vertical slice cuts through every layer — schema, API, UI, and auth where it applies — for one piece of real behaviour, instead of building all the database tables, then all the endpoints, then all the screens. Each slice below ends in something you can click through on the real domain, on real Postgres data, not a demo.

Slices 1–3 lean hard on the two prototypes you already have — most of that UI ports over close to as-is, the work is wiring it to a live API instead of localStorage. Slices 4 onward are net-new: units, leases, tenant accounts, and the maintenance workflow don't exist as real data yet.

0
Walking skeleton
Prove the full path — browser to Postgres and back — is real on your VPS before any feature is built on top of it.
Net-new
Data
  • New dedicated upkeep Postgres container in the VPS compose file — its own volume, not shared with other apps
  • users table (id, email, password_hash, role) — one seeded PM login
  • sessions table for cookie-backed sessions
Interface
  • POST /api/auth/login, POST /api/auth/logout
  • GET /api/health — round-trips a real query
  • Hono app scaffolded at apps/api, Drizzle schema at packages/db
Experience
  • React + Vite app at apps/web — login screen, blank authenticated shell
  • Caddy: subdomain routed to the web app, /api proxied to Hono
  • Session cookie gate — no page renders unauthenticated
✓
Ships whenYou log in on the real domain from your phone and see a shell that says "Connected" — sourced from an actual database query, not a hardcoded string.

Real photo storage
Property photos move out of base64-in-JSON and onto disk, so five photos per property doesn't mean five bloated database rows.
Net-new backend
Data
  • MinIO container (or bind-mounted volume) added to the compose file
  • property_photos — property_id fk, storage_key, position
Interface
  • POST /api/properties/:id/photos — multipart, streamed to storage
  • DELETE /api/properties/:id/photos/:photoId
Experience
  • Same 5-photo upload UI, swapped from FileReader.readAsDataURL to a real multipart request with a progress state
✓
Ships whenYou upload 5 photos from your phone at a site visit, then see the same 5 from a laptop across town.

Ops

How to sequence this

Non-negotiable
Slice 0 always goes first. Nothing else is worth building until login, one endpoint, and one page are proven on the real domain.
Fastest wins
Slices 1–3 move quickest — the UI already exists in Upkeep Property Pipeline, so most of the work is backend wiring, not new screens.
The backbone
Slices 4–7 are where the real net-new work is: units, leases, tenant accounts, and the maintenance workflow don't exist as data anywhere yet. Slice 6 is the actual product — everything before it exists to support tickets getting logged and closed.
Reorderable
Slices 9–11 can move around, or wait, based on what the business actually needs first — none of them block anything downstream.
Ongoing
Slice 12 isn't a one-time build — start the backup job as soon as Slice 1 has real data worth losing, and keep tightening it as the system grows.
Upkeep — built for a Guyana-based property sourcing & leasing operation. Self-hosted on the existing VPS, no third-party BaaS.
